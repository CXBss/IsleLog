# 隐私空间（Vault）设计

日期：2026-08-24
分支：`server-feat`（客户端） / 服务端（islelog-server，参考 `server-API.md`）
涉及仓库：本仓库（Flutter 客户端）；服务端需配合新增一个接口（见第 8 节）

---

## 1. 问题与威胁模型

日记里可能有一些不希望任何人（包括最亲密的人）看到的内容。现有产品完全没有锁屏/密码机制，所有内容对拿到已解锁手机的人都是明文可见的。

威胁模型：对方是**不懂技术**的人，但可能会翻文件系统、翻备份，未来也可能借助 AI 工具帮忙找线索。不需要防真正的技术攻击者，但要做到：

1. 界面上没有任何入口痕迹，不会被误触或看到
2. 磁盘上（包括备份）不出现明文内容，也不出现明显的"这里有个隐藏功能"的结构特征
3. 云端服务器只存密文

不追求的：抗专业取证、抗物理攻击、口令找回。口令忘记 = 数据永久丢失（提供可选恢复码兜底）。

## 2. 方案概述

- **入口**：主页搜索框输入预设口令回车，直接进入隐私空间页；未命中时行为与普通搜索失败完全一致（"未找到相关日记"），无法区分。
- **加密**：口令经 Argon2id 派生出一把密钥，加密整个隐私空间数据。磁盘上不存口令哈希或任何校验值——验证方式就是"能不能解开"。
- **存储**：两个不透明密文文件（`idx.bin` 存文字日记，`atc.bin` 存附件），没有 schema、没有 magic header，看上去就是随机字节。
- **视图**：隐私空间内是主库日记 + vault 日记的合并时间线，可筛选"仅隐私"。主库完全不知道 vault 的存在（标签、日历统计都不受影响）。
- **移入/移出**：可以把一篇已同步的普通日记连同附件一起转入 vault，原条目及其服务端版本历史被物理删除。
- **同步**：vault 内容伪装成一条"加密备份"memo 上传，客户端按内容前缀识别并跳过渲染，未设置口令的设备上无感知。

## 3. 密钥与加密

```
MK = Argon2id(口令, salt, m=32MB, t=2, p=1) → 32 字节
```

MK 直接用作 AES-GCM 密钥，加密/解密 `idx.bin` 和 `atc.bin`（两个文件共用同一把密钥和同一个 salt）。

依赖：[`cryptography`](https://pub.dev/packages/cryptography) ^2.9.0（纯 Dart，Argon2id + AES-GCM，全平台可用，无需原生绑定）。

**没有口令哈希**：磁盘上不留任何"待验证的秘密"。验证口令的唯一方式是用派生密钥尝试解密，GCM tag 校验通过即为正确。

**内存卫生**：密钥和解密出的明文只在解锁期间常驻内存，锁定时清空引用（`Uint8List` 承载，不经过 `String`）。不做更复杂的防护（防 GC 复制、防 swap 等）——对应的威胁模型（专业取证）不在防御范围内。

**恢复码（可选）**：首次创建 vault 时生成一个 24 位随机码，同样可解开数据（作为口令的等价物存在，用户自行决定是否使用、是否记录）。不设置也可以，代价是忘记口令即彻底丢失数据。

## 4. 入口与锁定

**创建**：搜索框输入 `+口令` 回车（`+` 前缀仅创建时使用一次），二次确认后生效。

**进入**：搜索框输入口令回车 → 直接推入隐私空间页，无任何过渡动画或提示。

**触发条件**：仅当输入内容长度 ≥ 8 且不含空格时才尝试解密，避免每次日常搜索都跑一次 Argon2。

**锁定时机**：
- 离开隐私空间页
- App 进入后台超过 60 秒

锁定 = 清空内存中的密钥与已解密数据，下次进入需重新输入口令。

## 5. 数据模型与视图

```dart
class VaultEntry {
  String id;                 // uuid
  String content;            // Markdown 正文
  DateTime createdAt;
  DateTime updatedAt;
  List<String> tags;         // 从 content 解析，仅存在于内存
  List<String> attachmentIds; // 对应 atc.bin 内的条目 id
  String? memosName;         // 已同步到服务端时的资源名
  String? movedFromMemosName; // 由普通日记移入时记录来源，纯审计用途
}
```

**合并时间线**：隐私空间页同时读取主库 Isar（`DatabaseService`）和内存中的 `VaultEntry` 列表，按时间归并展示，vault 条目带小锁标记。顶部提供"全部 / 仅隐私"筛选。日历、标签统计、往年今日在隐私空间内使用合并后的数据集。

**主库隔离**：vault 的标签、统计**不写入** `TagStat` 表或任何主库结构，只在内存中现算现用。这是隔离的关键——否则主页侧边栏的标签列表会泄漏隐私标签。

**搜索**：隐私空间内的搜索是解锁后在内存中对已解密内容做字符串匹配，不建索引。个人数据量级下足够快。

## 6. 附件

**存储格式**（`atc.bin` 加密前的明文体）：

```
[4B] 条目数
每条: [16B id][1B mime类型码][4B 长度][原始字节]
```

不采用 zip/压缩：照片（JPEG）、录音（AAC）本身已是压缩格式，DEFLATE 收益接近零，不值得引入额外依赖。

**重写策略**：`idx.bin`（纯文字，体积小）每次保存 vault 日记都整体重写；`atc.bin`（附件，体积大）只在增删附件时才整体重写。两者共用同一把密钥，用户感知上仍是"一个口令保护一个整体"。

**已知代价**：附件是整体重写，加一个新附件需要把 vault 内所有已有附件重新加密一遍。个人量级（几十个文件）内可接受，量级显著增长后会变慢——不在 v1 处理分片，先接受这个上限。

**查看时不落地明文**：
- 图片：`Image.memory(bytes)` 直接从解密后的字节渲染，不写临时文件
- 录音：`just_audio` 走内存字节音频源播放，不写临时文件

这条不是额外工作量，只是选对已有 API，但能避免"临时文件残留、被文件系统扫描发现"这一具体泄漏点。

## 7. 移入 / 移出

**移入**（普通日记 → vault）：
1. 读取原日记正文 + 附件原始字节
2. 写入 `VaultEntry` + 编码进 `atc.bin`（若有附件），整体重新加密
3. 服务端硬删除原 memo（见第 8 节接口）及其关联附件资源
4. 本地 `hardDelete` 原 `MemoEntry`（不能软删除——软删除仍会在本地留有明文内容字段）

**移出**（vault → 普通日记）：反向执行，新建 `MemoEntry` + 正常走现有同步逻辑，`VaultEntry` 从 vault 中移除。

## 8. 同步

vault 整体在解锁期间才参与同步。上传时伪装成一条"加密备份"memo：

```
content: "IsleLog-Backup/1\n<base64(idx.bin 密文)>"
visibility: PRIVATE
```

`atc.bin` 密文作为该 memo 的一个普通附件上传（文件名 `backup.dat`，mime `application/octet-stream`），复用现有 `AttachmentService` 的上传/下载逻辑，不需要新的传输通道。

客户端 `SyncService._applyRemoteMemo` 识别 `IsleLog-Backup/1` 前缀后直接跳过（不写入主库、不渲染），因此在未设置过隐私空间口令的设备上，这条 memo 只是静默存在，不会被看到。

**封面故事**：这条 memo 在服务端后台看起来就是一条"加密备份"记录，且客户端设置页会有一个真实存在的"加密云备份"开关与之对应（不是编造的伪装，是一个确实生效的功能点），经得起对方在 App 内核对。

### 服务端新增接口（阻塞项，需服务端配合）

```
DELETE /api/v1/memos/:id?hard=true   [IsleLog 扩展，待新增]
```

物理删除该 memo 行及其在版本历史表中的所有记录（而非现有 `DELETE` 的软删除 `row_status=DELETED`）。移入 vault 时客户端调用此接口而非普通删除。附件同理需要一个硬删除路径。

这一步客户端单独做不到——现有软删除会让"移入前的明文"永久留在服务端数据库和版本历史里。在服务端配合之前，移入功能应视为不完整（明文在服务端只是被隐藏，未被清除）。

## 10. 明确不处理的泄漏点

- 服务端管理员/数据库层面能看到密文体积和上传时间等元数据（无法消除，取决于服务端）
- 对方若已经知道存在隐私空间并索要口令，本设计不提供可否认的"假空间"机制（威胁模型已明确排除胁迫场景）
- 忘记口令 = 数据永久丢失，无后门找回
